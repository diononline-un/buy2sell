Backend & API

Technisch

Du hast Next.js gewählt — das bringt schon ein Backend mit. Die Frage ist jetzt: Wie strukturierst du den API-Layer? Next.js bietet mehrere Patterns: klassische API Routes, Server Actions, oder du trennst trotzdem ein eigenes Backend ab. Dazu kommt die Frage nach dem ORM und wie du Business-Logik (Versandkosten-Verteilung, Gewinnberechnung, Label-PDF) organisierst.

Server Actions + Prisma

React Components
↓ Server Actions
Service Layer
↓
Prisma ORM
↓
DB
Next.js Server Actions als primäres Pattern: Du rufst Backend-Funktionen direkt aus React-Komponenten auf — kein manuelles fetch(), keine API-Route-Dateien. Prisma als ORM für typsichere DB-Queries. Für Sonderfälle (PDF-Download, Bild-Upload) nutzt du einzelne API Routes. Das modernste und schlankeste Pattern.

Funktioniert gut wenn

  • Minimaler Boilerplate gewünscht
  • Typsicherheit end-to-end
  • Schnellste Entwicklungszeit
  • Kein separater API-Client nötig

Achtung bei

  • Neues Pattern, Debugging anders
  • Schwerer testbar als REST-APIs
  • Kein API für externe Clients

Klassisches REST-API-Pattern innerhalb von Next.js. Du baust /api/items, /api/hauls, /api/labels etc. als Route Handlers. Frontend fetcht ganz normal per fetch() oder SWR/React Query. Bewährtes Pattern, gut testbar, leicht erweiterbar. Etwas mehr Code als Server Actions, dafür klare Trennung.

Funktioniert gut wenn

  • Du REST-APIs gewohnt bist
  • API auch extern nutzbar sein soll
  • Klare Trennung Frontend/Backend

Achtung bei

  • Mehr Boilerplate pro Endpoint
  • Manuelles Error Handling nötig
  • Typsicherheit nur mit Extra-Setup

tRPC + Prisma

React + tRPC Client
↓ typsicher
tRPC Router
↓
Prisma ORM
↓
DB
tRPC gibt dir typsichere API-Calls ohne REST-Boilerplate. Du definierst Procedures (queries/mutations) in einem Router und rufst sie im Frontend typsicher auf — Autocompletion für Input/Output inklusive. Etwas mehr initialer Setup als Server Actions, dafür maximale Typsicherheit und gute Testbarkeit.

Funktioniert gut wenn

  • Maximale Typsicherheit wichtig
  • Komplexe Queries/Mutations
  • Gute Dev Experience gewünscht

Achtung bei

  • Zusätzliche Dependency + Setup
  • Overkill für einfache CRUDs
  • Lernkurve wenn neu

Separates Backend (Fastify)

Next.js (nur Frontend)
↓ fetch()
Fastify API Server
↓
Prisma ORM
↓
DB
Next.js nur als Frontend, separates Fastify (oder Express) als Backend. Zwei Docker-Container, klare Trennung, unabhängig skalierbar. Macht Sinn wenn du das Backend später für eine Mobile-App oder andere Clients wiederverwenden willst. Für ein Solo-Sideprojekt aber deutlich mehr Overhead.

Funktioniert gut wenn

  • Backend für mehrere Clients
  • Maximale Trennung gewünscht
  • Team-Szenario (FE/BE getrennt)

Achtung bei

  • 2 Container, doppelter Ops-Aufwand
  • Widerspricht Next.js Fullstack-Idee
  • Overkill für Solo-Sideprojekt
